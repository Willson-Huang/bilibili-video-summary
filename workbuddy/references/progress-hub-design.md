# 任务进度设计文档（progress_hub）

> 本文件是 `SKILL.md`「任务进度」章节的实现细节与调研记录。**用法看 SKILL.md，原理看这里**——这样 SKILL.md 只留可执行指令，实现笔记不占其篇幅。

## 一、为什么自建

现成的进度项目（tqdm / rich / enlighten / alive-progress / textual）都要往 venv 里装包，而那套环境里 `funasr` 与 `faster-whisper` 本就存在依赖冲突。本方案零依赖（stdlib only）、不联网，跨两个 venv 都能跑，字段与显示完全由自己掌握。

## 二、数据流：事件流

写入端由管线各进程调用 `emit()`，把事件追加到自己那份 `<运行目录>/events_<进程号>.jsonl`；读取端 `--status` 聚合 `run.json`、未退役的 `events_*.jsonl` 与 `state_snapshot.json`，算出当前进度并打印。

- **每进程写自己的事件文件**：不抢锁、不会交错损坏，某个进程崩溃也只丢自己那一份
- `run.json` 存任务清单（标题 / UP主 / 时长 / 引擎），可选；不建也能跑，任务信息会从事件里推断
- 阶段**按序推进**（`STAGE_RANK`）：迟到的旧阶段事件不会把显示拉回去；`done` / `fail` 同阶，后到者生效

## 三、百分比算法（估算）

Nano 一次 `generate` 处理整条音频，**没有细粒度回调**，所以：

- **阶段**：排队 → 下载 → 转码 → 转写 → **待生成纪要** → 生成纪要 → 完成；wiki 编译侧另有一条 **待编译** → 完成。由脚本在边界上报，这一段是精确的。转写脚本只报到「待生成纪要」，`done` 由**写完纪要**的一方发出 —— 让转写脚本直接发 `done` 会让进度提前宣布完成，而模型侧的纪要耗时恰好是最大的一块
- **一条视频是两条任务**（2026-10-02）：转写侧以 `BV号` 登记（终点＝纪要写完），编译侧以**纪要文件名**登记（终点＝编译进 wiki），靠 `group` 区分。转写侧显示「已完成」**不代表整条链路走完** —— 编译还没做的必须显式列为「待编译」，否则进度会显示成整批全部完成（实盘 2026-10-02：4 条只到纪要，却报 27/27 全完成）
- **单条百分比**：按「已用时间 ÷ (音频时长 ÷ 倍率)」插值，上限截到 97%，避免"永远差一点"。倍率随样本变化，按三档取（`effective_rtf`）：本批实测 → 批量兜底 2.1x → 单条常量（Nano 5.08x / whisper 19.2x，取自 `references/perf-benchmark-2026-09-13.md`）。常量按单条标定，批量实测只有约 2.1x（5 条 / 3225.5 秒音频 / 1555 秒），照常量算会在转写中途直接顶到 97%。实测值对样本按时间顺序做**指数平滑**（`_ema`：`alpha=0.3`，算式与 tqdm 的 `EMA` 同源，含 `1-(1-a)^n` 误差修正），所以「批次突然变慢」比取中位数反映得更快
- **预计剩余**：只有「排队」和「转写中」两种情形有依据 —— 前者给整段预测，后者给「预测 − 已用」。下载 / 转码 / 生成纪要 / 待编译**没有各自的实测样本，不给数字**（显示「—」），套用转写预测会失真；已用超过预测时显示「已超预估」而不是「剩 0s」。⚠️ 累加只能用**行自己的 `eta`**，不能拿 `pred_sec` 乘剩余比例：待编译这类人工阶段自带预估秒数、百分比又是 0，会被当成「还没开始跑」算出一个根本不存在的完成时刻
- **总进度**：按各任务预测耗时**加权**，避免把一条 38 分钟的和一条 20 分钟的任务算成同等份量；**分母排除失败行** —— 失败行会残留中断时的百分比，算进去就永远到不了 100%
- **「已耗时」是各已完成任务的实测耗时合计**（2026-10-02 改）：原先算的是「当前时刻 − 运行目录建立时刻」，而 `created` 在 `init_run` 合并时保留首个写入者、运行目录又不按批次隔离 → 量到的是目录存在了多久（实盘 415h06m41s ＝ 17.3 天，而任务耗时合计只有 3h41m）。它是累加值，不随本地时钟推进。显示上超过一天改用「天 + 时 + 分」
- **跨批次历史只显示、不参与计算**：`rtf_history.jsonl` 记在**运行目录的上一级**，每引擎最多 50 条，只写 `engine` / `rate` / `ts` 三个字段（不写素材名也不写时长）。「本批实测」与「历史中位」并排显示，换机器 / 换模型版本 / GPU 被占用这类变化由人判断 —— 同 Airflow 的 Task Duration 视图，只给参照，不做自动采用
- **转写中顺带显示实测速率**：`音频秒数 ÷ 已用秒数`，让「预计剩余」有个可核对的依据。拿不到速率的阶段不编数字

## 四、事件文件治理

事件文件按进程累积，跑多批后用 `--compact` 折叠成 `state_snapshot.json`，并退役（删除）已静默超过 5 分钟的文件；**正在跑的进程文件不会被删**（`--safe-age` 可调，`--dry-run` 只预演）。`--compact` 同时把跨批次历史裁到每引擎最近 50 条（那个文件是 append-only 的，会一直长）。

## 五、事件角色（kind，可选）

借 LSP 的 Work Done Progress：`emit(kind=...)` 取 `begin` / `report` / `end`，描述这条事件在**它自己那个阶段**里的位置。转写侧的三段式是现成的例子：首条 `asr` 事件带 `begin`、每 3 秒的插值带 `report`、转写完成带 `end`。

**它只让事件流自描述，不参与状态推导。** 状态仍从事件内容（`stage` / `pct` / `elapsed`）算出来，不依赖事件顺序 —— 乱序容错保持不变。取值不在白名单里就当没传（静默丢弃）。

## 六、已知问题

- **管线进程崩溃后，进度会在 5 秒内看起来"还在跑"** —— 之后外推被 `STALE_CAP` 截住、数字停住。进程没了就没人上报 `fail`，状态只能靠数据龄提示
- **首个批次的前两条任务仍按常量估算**：实测倍率至少需要 2 条「转写完成」事件才有样本；样本到位前，音频任务 ≥ 2 条时用批量兜底值 2.1x，单条运行才用 5.08x

## 七、批次隔离：一个批次一个运行目录（2026-10-02）

在此之前，所有批次共用一个 `run.json`：`init_run(merge=True)` 把新批次**并入**旧清单，`created` 又被首个写入者锁住。后果是三重的 —— 任务越滚越多、「已耗时」量成了目录年龄（415 小时）、跨批统计无从区分。

现在的做法：**运行目录名固定是 `current`，隔离发生在「开新批」那一步**。目录形态：

- `current/` —— 本批（转写与编译都写这里）
- `batches/<时间>-<来源>/` —— 归档批次，整份搬来
- `rtf_history.jsonl` —— 跨批次历史，在运行目录的上一级，不动

- **触发**：`init_run(..., new_batch=True)` 先把 `current` 整份搬进 `batches/<时间>-<来源>/`，再重建一个空的 `current`。只有「开始一次新运行」的一方传这个参数 —— 补数据、登记待编译的一方不能传，否则会把自己刚写进去的东西一起搬走
- **两边脚本零改动**：转写脚本照旧写 `current`、读取侧照旧读 `current`，谁都不必知道批次的存在。名字固定是关键，换来的是不必同步改三副本的下游
- **空目录不轮转**：`current` 里既没有 `run.json` 也没有事件时直接返回，否则连续开批会留下一串空目录
- **换目录不用改配置**：`rtf_history.jsonl` 在运行目录的上一级，跨批次历史照旧累积

命令行：`--status` 打印当前批次的纯文本进度（读同一份 `snapshot()`）；`--list-batches` 列出归档批次；`--init --new-batch` 手工开一批。

## 八、命令行查看与启动器

长任务（10 条 × 25 分钟音频约 1 小时）需要随时看到每条任务在做什么、走到几成、还剩多久。进度数据由管线各进程上报事件流，查看方式是 `--status`：读同一份快照、打印纯文本。

```bash
python scripts/progress_hub.py --status          # 当前批次：整体进度、每条任务的阶段与耗时
python scripts/progress_hub.py --json            # 同一份内容的 JSON 版，给脚本与外部程序读
python scripts/progress_hub.py --list-batches    # 列出已归档的批次
```

**连着盯屏幕**：用随技能带的启动器，每两秒清屏重打一次。

```bash
scripts\progress_watch.bat                 # Windows：在项目目录里运行（也可双击）
scripts\progress_watch.bat <项目根>         # 显式指定项目目录
./scripts/progress_watch.sh                # macOS / Linux
```

启动器自己找进度目录：先看参数，再看 `BILI_PROGRESS_DIR`，都没有就从当前目录向上找含 `.workbuddy` 的目录。找不到会打印提示并停住，不会一闪而过。Python 解释器按 `BILI_PYTHON` → 常见安装位置 → `PATH` 依次探测（macOS / Linux 用 `python3`）。文件里不含本机路径，随技能复制到别的机器可直接用。

⚠️ 百分比是插值估算，不是精确进度：Nano 一次 `generate` 处理整条音频、没有细粒度回调，单条百分比按「已用时间 ÷（音频时长 ÷ 实测倍率）」插值，上限截到 97%。倍率取三档（本批实测 → 批量兜底 2.1x → 单条常量），来源随状态一并给出。阶段边界由脚本上报，这一段是精确的。

## 九、上报机制

上报默认开启：转写时自动登记任务。运行目录未设时按项目推导，`_ensure_progress_dir()` 只做 `setdefault`、不覆盖显式配置：

1. `BILI_PROGRESS_DIR` 已设，用它，不再推导
2. `BILI_PROGRESS=off`，不启用
3. 否则从当前目录向上找含 `.workbuddy` 的目录，得到 `<该目录>/.workbuddy/cache/progress/current`
4. 都找不到，不启用（绝不在任意当前目录下创建）

批次隔离见第七节。手工开一批用 `progress_hub.py --init --new-batch --tasks <清单文件或 JSON 字符串>`。两条操作禁忌：补数据、登记待编译的一方不要传 `new_batch`，否则会连自己刚写进去的一起搬走；`--init` 别顺手加 `--new-batch`，它会把当前批次整体归档再开新批。

⚠️ 上报环节的 `try/except` 全吞：运行目录解析失败或上报未启用时，退出码仍是 0、零日志，从外部看不出被跳过。要确认在跑，看运行目录下有没有 `events_*.jsonl`。

```bash
BILI_PROGRESS=off python bili_asr.py ...        # 单次关闭
```

两个技能共用一个运行目录：`init_run()` 是并入语义，不是替换——转写与 wiki 编译的任务清单在同一个 `run.json` 里共存，靠 `group` 字段区分。

| 场景 | 谁上报 | 方式 |
|---|---|---|
| 转写 | `bili_asr.py`（下载与转码阶段）+ `funasr_adapter.py`（转写阶段） | 自动 |
| 生成纪要 | 主 agent | `notes_done.py` 对账补发（原先靠命令行 `--emit`，实测漏发 7 次） |
| 其它脚本 | 任意进程 | `import progress_hub; progress_hub.auto(task=..., stage=..., pct=...)` |

**批量必须走 `_prog_boot` 登记，且只登记一次**：

| 症状 | 根因 | 修法 |
|---|---|---|
| whisper 批量一条都没登记 | 批量分支只在 `engine == 'funasr-nano'` 时调 `_prog_boot`，whisper 批量整段没登记 | 批量分支统一调 `_prog_boot(_p, items, engine=a.engine)` |
| 批量跑完 `current/run.json` 只剩最后一条 | `process_video` 每条都传 `new_batch=True`，每条把上一条刚写的清单搬进归档 | 加 `in_batch` 参数：批量调用传 `True`，只上报阶段、不开新批次 |

上报点：转写脚本只报到 `transcribed`（待生成纪要），「已完成」由写纪要的一方发出。`--kind` 是可选的事件角色（`begin` / `report` / `end`），只为让事件流好回看，不影响状态判定。

「已完成」原先靠人工执行 `--emit`，实测累计漏了 7 次（3 次发到了纪要文件名下、4 次完全没发），任务长期挂在「待生成纪要」。现改为对账：`notes_done.py` 扫出进度里停在非终态的 BV 任务，把它名下的素材包（含多 P 的 `bili_<BV>_p<页>.md`）一并找齐，每一页都配上标准纪要文件才补发完成信号。配不上就跳过并说明原因（素材包不存在 / 头部缺字段 / 纪要不在目录 / 标点归一化后撞出多个候选 / 还有哪几页没写纪要），绝不编造完成。输出里 `note_files` 与 `pack_files` 是本次配对到的全部文件，`pending` 是登记了哪些「待编译」。

转写侧的「已完成」只到纪要，编译是另一件事。补发完成时会顺带登记一条「待编译」（编译侧以纪要文件名登记，`group` 是 `wiki编译`）。少了这一步，进度会把「只到纪要」显示成整批全部完成——实盘出现过 4 条没编译、进度却报 27/27 的情况。不打算编译的批次加 `--no-pending` 关掉。

```bash
python scripts/notes_done.py                # 运行目录、纪要目录、素材包目录自动推导
python scripts/notes_done.py --dry-run      # 只列出会补哪些，不上报
python scripts/notes_done.py --no-pending   # 只补完成，不登记待编译
```

台账流程不用手动跑：`library_queue.py --finish` 回写「已完成」成功后会顺带补发该条。

报告「生成纪要中」时仍可手动划出起算点：

```bash
python scripts/progress_hub.py --emit --task <BV号> --stage notes --kind begin --note '生成纪要中'
```

## 十、设计约束

- 上报是旁路：`emit()` 内部 `try/except` 全吞，任何异常都不影响转写；`BILI_PROGRESS_DIR` 未设置时连模块都不导入
- `--status` 只读运行目录，不写任何管线产物，可随时运行，不影响正在跑的任务
