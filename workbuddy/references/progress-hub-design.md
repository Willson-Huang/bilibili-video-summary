# 进度看板设计文档（progress_hub）

> 本文件是 `SKILL.md`「进度看板」章节的实现细节与调研记录。**用法看 SKILL.md，原理看这里**——这样 SKILL.md 只留可执行指令，实现笔记不占其篇幅。

## 一、形态选型（2026-09-13 调研）

GitHub 上**没有可直接集成的现成方案**：

| 候选 | 为什么不用 |
|---|---|
| tqdm / rich / enlighten / alive-progress | 都是"终端里的进度条"，成不了独立窗口 |
| textual（37.2k★） | 能做出漂亮 TUI，但要往有依赖冲突风险的 venv 里装包 |
| `babysitter-observer-dashboard`（24★） | 形态接近，但绑定其自有 agent 协议 |

故自建：**stdlib-only 本地看板 + 浏览器 `--app` 独立窗口**。零依赖，跨两个 venv 都能用，样式完全自由。

## 二、单实例：三层保证与踩坑

不加单实例的话，跑 20 条视频会弹 20 个窗口。实现由三层保证：

1. 服务启动时把**实际端口**写进 `<运行目录>/hub.json`（端口被占用回退后也准确）
2. 探测只读该文件 + 探默认端口，**不做端口扫描**——本机探测关闭端口要等满超时，扫 24 个就是 7 秒
3. 探测用**裸 socket 累积读到 `"ok"`**，不用 `urllib`

> 两条都是实测踩出来的：`urllib` 会读系统代理设置，请求 `127.0.0.1` 可能被代理劫持（关闭端口等满超时、服务在跑也误判"没跑"，导致重复弹窗）；而单次 `recv` 可能只拿到响应头（body 在下一个 TCP 段），三次探测里两次误判。

## 三、数据流：事件流，不是驻内存服务

```
管线进程  --emit-->  <run_dir>/events_<pid>.jsonl   （每进程独立文件，无锁、不交错）
                          |
看板服务  --聚合-->  run.json + 全部 events_*.jsonl  -->  /api/state  -->  dashboard.html 每 700ms 轮询
```

- **每进程写自己的 events 文件**：不抢锁、不会交错损坏，某个进程崩了也只丢自己那份
- `run.json` 存任务清单（标题 / UP主 / 时长 / 引擎），可选；不建也能跑，任务信息会从事件里推断
- 阶段**按序推进**（`STAGE_RANK`）：迟到的旧阶段事件不会把显示拉回去；`done` / `fail` 同阶，后到者生效

## 四、百分比算法（估算，不是精确进度）

Nano 一次 `generate` 处理整条音频，**没有细粒度回调**，所以：

- **阶段**：排队 → 下载 → 转码 → 转写 → **待生成纪要** → 生成纪要 → 完成。由脚本在边界上报，这个是精确的。转写脚本只报到「待生成纪要」，`done` 由**写完纪要**的一方发出 —— 让转写脚本直接发 `done` 会让看板提前宣布完成，而模型侧的纪要耗时恰好是最大的一块
- **单条百分比**：按「已用时间 ÷ (音频时长 ÷ 倍率)」插值，上限截到 97% 避免"永远差一点"。倍率**不是常量**，按三档取（`effective_rtf`）：本批实测 → 批量兜底 2.1x → 单条常量（Nano 5.08x / whisper 19.2x，取自 `references/perf-benchmark-2026-09-13.md`）。常量按单条标定，批量实测只有约 2.1x（5 条 / 3225.5 秒音频 / 1555 秒），照常量算会在转写中途直接顶到 97%。实测值对样本按时间顺序做**指数平滑**（`_ema`：`alpha=0.3`，算式与 tqdm 的 `EMA` 同源，含 `1-(1-a)^n` 误差修正），所以「批次突然变慢」比取中位数反映得更快
- **预计剩余**：只有「排队」和「转写中」两种情形有依据 —— 前者给整段预测，后者给「预测 − 已用」。下载 / 转码 / 生成纪要**没有各自的实测样本，不给数字**（显示「—」），套用转写预测是错的；已用超过预测时显示「已超预估」而不是「剩 0s」
- **总进度**：按各任务预测耗时**加权**，不是简单条数平均（否则一条 38 分钟的和一条 20 分钟的一样重）；**分母排除失败行** —— 失败行会残留中断时的百分比，算进去就永远到不了 100%
- **跨批次历史只显示、不参与计算**：`rtf_history.jsonl` 记在**运行目录的上一级**，每引擎最多 50 条，只写 `engine` / `rate` / `ts` 三个字段（不写素材名也不写时长）。顶部把「本批实测」与「历史中位」并排显示，换机器 / 换模型版本 / GPU 被占用这类变化由人判断 —— 同 Airflow 的 Task Duration 视图，只给参照，不做自动采用
- **转写中顺带显示实测速率**：`音频秒数 ÷ 已用秒数`，让「预计剩余」有个可核对的依据。拿不到速率的阶段不编数字（rich 在总量未知时显示速度，思路一致）

## 五、时间显示：本地时钟推进（2026-09-14）

看板上的「最后更新 / 已耗时 / 剩余」**不是轮询一次刷一次**，而是服务端给基准值、本地时钟按 `UI_TICK`（500ms）平滑推进。

原因：轮询周期 700ms、显示粒度 1 秒，两者不同步 → 相邻两次采样会跨 0/1/2 个秒边界，肉眼所见就是"停一下、跳两秒"，节拍忽快忽慢（服务端时钟本身没问题）。轮询同时改为**按目标时刻排期**，不再"响应后再等 700ms"，否则周期会变成 700ms+RTT，抖动进节拍且误差随时间累积。刷新间隔取 500ms：rich 的 `TimeRemainingColumn` 用 0.5s，理由同样是防抖动；本看板的过期判定是秒级、十秒级量级，250ms 对它是浪费。

四条约束：

- **终态冻结**：`done` / `fail` 的任务不参与外推，显示事件里记录的真实耗时，不会一直涨
- **外推上限（`stale_cap`，默认 5s）**：服务端把基准截在「最后**一条事件**时刻 + 5 秒」（`eff_now`），前端两次轮询之间的外推用同一个额度。两侧同源，停更后数字停住，不把"卡住"演成"还在跑"。三个阈值（`stale_cap` / `stale_warn` / `stale_bad`）**都随状态下发**，前端只留兜底值 —— 它们与上报频率耦合，换引擎或改上报间隔时要能一处改完；`stale_warn` / `stale_bad` 还按当前阶段取值，见下条
- **数据龄以事件为准**：服务端报 `stale_sec`（距最后一条事件多久），前端再加本地经过的时间。**只看本地收包时刻是错的** —— 轮询成功不等于管线有产出，那样管线卡住也会一直显示"刚刚"，两档着色永不触发
- **「最后更新」用相对时间**（`刚刚` / `12 秒前`）：绝对时刻一直在跳不等于数据在更新，相对时间才可判断。超过 `stale_warn` 转黄、`stale_bad` 转红；两者**由当前阶段的心跳间隔推出**（转黄 = 心跳秒数，转红 = 3 倍心跳），心跳表在 `STAGE_HEARTBEAT`：下载 / 转码 / 转写 10s，排队 / 待生成纪要 / 生成纪要 300s，终态 3600s；不在表里的阶段回落兜底 10s / 30s。载荷带 `stale_stage` 说明取值来自哪个阶段 —— 「生成纪要」由主 agent 写完才上报一次，中间几分钟没有事件是正常的。页面切到后台时**不着色**（浏览器会给后台标签页降频，那时的数据龄不代表异常）

> 回归测试：`node tests/test_dashboard_times.js`（桩 DOM + 可控时钟，49 条断言）。Python 单测看不到 dashboard.html 里的 JS，而这里踩过三次静默失效（`tick()` 漏写基准赋值、`ago()` 未定义、`renderTasks` 忘了给节点挂 `t`），表现都是数字冻结在旧值、页面无任何报错——故单独加一个 JS 测试。
>
> **桩必须让 `renderTasks` / `makeRow` 真正跑完**：早期版本的桩把 `querySelector` 写成恒返回 `null`，等于跳过整条渲染路径，于是「节点没挂 `t`」这类断线问题测不出来（17 条断言全绿，而任务行的时间一直不更新）。测试支持传入另一个 dashboard.html 路径，便于拿"退回修复"的副本反证它确实拦得住。

## 六、事件文件治理

事件文件按进程累积，跑多批后用 `--compact` 折叠成 `state_snapshot.json`，并退役（删除）已静默超过 5 分钟的文件；**正在跑的进程文件不会被删**（`--safe-age` 可调，`--dry-run` 只预演）。`--compact` 同时把跨批次历史裁到每引擎最近 50 条（那个文件是 append-only 的，会一直长）。

## 七、事件角色（kind，可选）

借 LSP 的 Work Done Progress：`emit(kind=...)` 取 `begin` / `report` / `end`，描述这条事件在**它自己那个阶段**里的位置。转写侧的三段式是现成的例子：首条 `asr` 事件带 `begin`、每 3 秒的插值带 `report`、转写完成带 `end`。

**它只让事件流自描述，不参与状态推导。** 状态仍从事件内容（`stage` / `pct` / `elapsed`）算出来，不依赖事件顺序 —— 乱序容错保持不变。取值不在白名单里就当没传（静默丢弃）。看板把它带在任务行与事件流里，方便回看「这个阶段是刚开始还是快结束了」。

## 八、已知问题

- **管线进程崩溃后，看板会在 5 秒内看起来"还在跑"** —— 之后外推被 `STALE_CAP` 截住、数字停住，同时「最后更新」开始转黄、转红。进程没了就没人上报 `fail`，状态只能靠着色提示。
- **首个批次的前两条任务仍按常量估算**：实测倍率至少需要 2 条「转写完成」事件才有样本；样本到位前，音频任务 ≥ 2 条时用批量兜底值 2.1x，单条运行才用 5.08x。
- 两个 skill 共用同一窗口时，`run.json` 的任务组靠 `group` 字段区分；若两个 skill 同时首次启动看板，存在极小的竞态窗口（未观察到实际问题）。
