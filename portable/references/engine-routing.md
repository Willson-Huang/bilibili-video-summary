# 引擎路由与切换

决定一件事：这条视频走哪条路由、用哪个引擎、什么时候切。默认 `whisper`，Nano 需要显式 opt-in。

## 一、两引擎实测对比

两段独立 60s 样本，基准取人工 CC 字幕：

| 模型 | 专名正确率 | 典型表现 |
|---|---|---|
| whisper-large-v3-turbo | 2/11（18%） | 肇庆→赵庆、怀集→淮吉、利玛窦→立马逗、赵佶→赵吉 |
| **Fun-ASR-Nano-2512（800M）** | **10/11（91%）** | 肇庆/怀集/赵佶/端王/利玛窦全对，仅「立桥楼→历桥楼」近似错 |
| Qwen3-ASR-1.7B | 7/11（64%） | **肇庆→赵庆（同 whisper 错）**、利玛窦→利马窦 |

速度（NVIDIA RTX 4060 Ti 8GB）：

| 场景 | 实测 |
|---|---|
| whisper large-v3-turbo | **19.2x** 实时（1483s 音频转 77.4s） |
| whisper turbo + `initial_prompt` 专名提示 | 20.7x，提速无损失，但救不了专名 |
| Fun-ASR-Nano-2512（800M） | **5.1x** 实时（180s→35.5s；1483s→286s） |
| Nano 模型冷启动 | 48–52s，每批只付一次 |

Nano 的约 5x 是上限，调参杠杆逐项实测无效：`batch_size` 1→4/8/16 得 5.07 / 5.01 / 5.06 / 5.04x；VAD 段长 30/60/120s 得 5.08 / 5.08 / 5.11x；热词 0 词与 37 词为 35.5s 与 39.9s（同量级）；1483s 长音频仍 5.08x；双进程总算力 2.01x 对单进程 1.93x，加速比仅 1.04x。逐项数据与复现命令见 `perf-benchmark-2026-09-13.md`。

**排期按单条 5x 算，批量要留余量**：5 条中文口播（合计 3,225.5s 音频）批量实测整批 1,555s ≈ 2.1x，明显低于 5.1x；同批单条（502s 音频）剔除冷启动后约 4.2–4.8x，接近基线。差额归因未定位，疑与逐条下载转码、逐段热词注入有关。单条按 5x 估，批量按 5x 估完再加 1.5–2.5 倍余量，不要用 5x 直接外推长批次。

## 二、分流规则

| 内容类型 | 引擎 | 理由 |
|---|---|---|
| 有**人工 CC 字幕**（`zh-CN`） | 字幕直取，不用 ASR | 人工产出，可信度最高，优先 |
| 只有 **AI 字幕**、专名密集（历史/地理/政经） | `--force-asr --engine funasr-nano` | 两路独立识别、错点不同，双源才有对照价值；Nano 专名 91% 对 whisper 18%。**只带 `--engine` 等于什么都没做**——字幕路由在 ASR 之前，不带 `--force-asr` 引擎根本不启动 |
| 只有 **AI 字幕**、内容泛科技/口语向 | 字幕直取 | 非专名场景两路差异小（实测 30s 窗内容一致），秒级到手 |
| 泛聊天 / 通用科技 / 快速批量初筛 | `whisper`（默认） | 速度快、常驻成本低 |
| 需要逐字引用 + 专名密集 | `funasr-nano` + `--hotwords` | 热词进一步兜底近音地名 |

触发 Nano 的条件（满足任一即考虑，不要只看置信度——whisper 的「肇庆→赵庆」很可能是高置信度错）：

- 频道/视频类别属高专名风险（历史、地理、纪实、政经）
- 文本出现疑似音译地名/人名
- 两个引擎结果不一致时，以 Nano 为准

## 三、切换信号

脚本本身**不做内容类型识别**，`--engine` 必须显式传；切换决策由接收任务时按下表判断，把参数写进命令。

| 信号类型 | 具体清单（基于已处理视频的实测归类） |
|---|---|
| **UP主白名单**（历史/地理/政经） | 命中 `engine_up_whitelist.txt` 中已登记且经实测的 UP主 |
| **标题关键词** | 省/市/县/区地名（肇庆、怀集、湛江、茂名、海南、东南亚…）、朝代与历史人物（宋徽宗、赵佶、明朝、客家…）、政经实体（霍尔木兹、G7、财政、化债…）、系列名（「XX 里的中国」「XX 为什么」） |
| **内容特征** | 同一段口播里出现 2 个以上陌生专名；人物/地名/机构密集 |
| **字幕形态 + 内容类型** | 视频只有 AI 字幕（`ai-zh`）且内容专名密集 → 必须**同时**带 `--force-asr`；产出后本地转写为主源、AI 字幕作旁证 |

## 四、明确不切

| 情形 | 原因 |
|---|---|
| 视频有**人工 CC 字幕** | 字幕优先，切引擎无效（字幕路由在 ASR 之前） |
| 泛科技 / AI 产品向、方法论类 | 英文产品名与术语多，Nano 英文 token 会粘连；whisper 快约 20x |
| 英文歌、纯英文内容、音乐 MV | Nano 对外语不占优 |
| 快速批量初筛、只想看个大概 | 速度优先 |

**归类以内容主体语言为准，不按领域标签**：某财经类 UP主 虽涉 AI 与政治，但叙述主体是中文财经专名（化债、财政体系、大厂资本），判 Nano；某科技类 UP主 主体是英文产品名（OpenClaw、WorkBuddy、Agent），判 whisper。判据是「专名用什么语言写」。

## 五、执行模板

```bash
# 命中信号 → 一律强制本地转写。不要先判断「有无字幕」再决定带不带 --force-asr：
# 判断本身会出错（探测脚本漏初始化 cookie 时字幕恒为空），带 --force-asr 可免于误吃 AI 字幕
bili_asr.py <链接> --force-asr --engine funasr-nano --hotwords <临时热词文件> --out <素材包>

# 只想先看有无字幕与引擎建议：--only-meta --classify
```

**切换时同步带热词**，否则只发挥一半效果：从标题、简介、UP主名抽取 20–50 个专名写入临时热词文件（去重、硬上限 80），用 `--hotwords` 传入。临时热词文件放 `%TEMP%`，不要写进技能目录，批量跑完即删。

**误切的代价**：慢 3–10 倍，英文内容质量下降。**漏切的代价**：吃下 AI 字幕，专名级错误无人对照，比 whisper 更差——本地转写至少错点可查、可与字幕互校。专名密集内容拿不准时按「切」处理；只有泛科技、口语、外语内容按「不切」。

## 六、新 UP 主判定：`--classify`

脚本内置 `--classify`，不用下载音频、不跑 ASR，只读 view 元信息（走 24h 缓存，0.3s）给出引擎建议：

```bash
bili_asr.py <链接或BV> --only-meta --classify
# 返回 engine_suggestion: {engine, confidence, source, reason, hits}
```

| 优先级 | 信号 | 置信度 | 可靠性 |
|---|---|---|---|
| 1 | **UP主白名单** `engine_up_whitelist.txt` | `high` | 最准（已验证的） |
| 2 | **视频 tag**（官方 `x/tag/archive/tags` 接口） | `high` | **比分区准**：实测地理科普视频的 tag 全是地名 |
| 3 | **分区 tid_v2**（可选，需本地补充映射表） | `mid` | 仅供辅助：实测地理类视频被归到「知识·商业财经」 |
| 4 | 标题/简介关键词 + 模式打分 | `mid` / `low` | 无词典维护成本，兜底 |
| 5 | 默认 | `default` | whisper |

分区信号为什么只排第 3：B站分区由 UP主 投稿时自选，地理科普类会被归到「知识·商业财经」或「生活·日常」；视频 tag 由 UP主 与观众共同产生，直接反映内容主题，实测准确率明显更高。映射表缺失时脚本自动降级，只跳过该信号。

**代价不对称**：漏切维持现状；误切慢 3–10 倍且英文质量下降。灰区（score 0 或 `low`）一律判 whisper。

## 七、数据源与合规

| 信号 | 来源 | 合规状态 |
|---|---|---|
| 视频 tag | 官方公开接口 `x/tag/archive/tags` | 公开接口，主信号 |
| 标题 / 简介 / UP主 | view 接口公开字段 | 公开 |
| 分区 tid_v2 映射 | 第三方整理的接口文档 | **本地私有补充，不随发布脱敏版分发** |

分区映射表不随发布版分发的原因：该映射源自第三方「B站非公开接口文档」整理项目，该项目已被 B站委托律所发函后关停并删除全部文档（指控其系统性整理并公开非公开 API 的调用逻辑与参数结构）。

**本地保留、对外移除**：发布脱敏版不含此类映射表；已装副本里的 `bilibili_tid_v2_map.txt` 是安装器回填的私有补充，使用中有效，不要删除（删了分区信号降级，不影响主流程）。对外分发前必须先移除该文件。

## 八、白名单自学习

1. 新 UP 主首次处理，用 `--only-meta --classify` 拿关键词建议
2. 按建议跑完后，对照人工 CC 字幕或常识核对素材包里的专名
3. 结论确认后追加一行到 `engine_up_whitelist.txt`（5 列：`UP主名 | 引擎 | 依据 | 确认日期 | 依据类型`）。第 5 列填「实测验证」或「标题归类」，`--classify` 靠它算 `verified`，漏填会让该条永远被判为未验证
4. 下次同 UP 主直接 `high` 命中白名单，不再猜。判错的条目不要删，改判并留一行修正说明

规则写在技能正文（供阅读），数据写在 references（可增量、可审阅）。不做黑盒自动学习——误判污染白名单的代价高于人工确认一行。

## 九、自迭代验证

白名单里只有部分 UP 主经过实测，其余是标题推断。不专门跑验证任务，在每次真实处理视频时顺带完成，成本趋近于零。

```
--classify 提示 verified=false（待验证）
        ↓
按建议跑完视频（正常任务，不为验证而跑）
        ↓
顺带做一次专名核对（下面三种方式，选最便宜的）
        ↓
结论写回：① 白名单依据类型改「实测验证」+ 附 BV 例证
          ② 追加一行到 engine_verify_log.txt
        ↓
下次同 UP 主 classify 显示 verified=true，不再提示
```

| 方式 | 成本 | 适用 | 操作 |
|---|---|---|---|
| **人工 CC 对照** | 零额外 ASR | 视频有**人工 CC 字幕** | 拿人工 CC 与本地转写对比专名。AI 字幕不可作基准——它是另一路中文识别，专名同样会错 |
| **常识核对** | 零 | 任何 | 读素材包正文，凭常识判断专名是否被错写（「险性债务」应为「隐性债务」） |
| **双跑抽样** | 约 1–2 分钟 | 存疑、上面两种定不了 | 只跑前 60–90 秒，whisper 与 Nano 各一次对比 |

双跑只跑片段：全片双跑要十几分钟，片段足够看出同音混淆模式（whisper 的典型错误是「隐性→险性/隐姓」这类同音替代，前 90 秒就会暴露）。

判错的处理：不删原记录，改判并留修正说明。例：某财经类 UP主 原判 whisper，实测后改判 Nano，白名单与日志都保留改判痕迹与依据。

`--classify` 对未实测的 UP 主会返回 `verified: false` + `verify_hint`，看到就应在本次任务收尾时顺带核对。

**类别 → 建议引擎**（发布脱敏版不含私人白名单，可直接作为自己的起点）：

| 内容类别 | 建议引擎 | 依据 |
|---|---|---|
| 历史 / 地理 / 地方志（地名、朝代、古迹密集） | funasr-nano | 实测：Nano 专名 10/11 对 whisper 2/11 |
| 财经 / 政经（机构名、政策术语密集） | funasr-nano | 实测：Nano 债务类术语全对，whisper 同音错 5 处 |
| 国际政经（国名、机构、人名密集） | funasr-nano | 标题归类 |
| 泛科技 / AI 产品（英文产品名、技术术语多） | whisper | 标题归类；Nano 英文 token 易粘连 |
| 方法论 / 社会议题（非专名密集） | whisper | 标题归类；whisper 快约 20x |

白名单与验证日志在发布脱敏版里不存在（属个人观看记录），已装副本里由安装器回填，它们是 `--classify` 判 `high` 的依据，不要删除。
