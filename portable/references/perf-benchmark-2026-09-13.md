# ASR 引擎性能基准（2026-09-13）

> 本文是 SKILL.md「速度」章节与「已验证不可用的提速方案」的**原始实测依据**。
> 起因：Fun-ASR-Nano 实跑明显慢于 whisper，需要判定「是配置问题还是架构上限」。

## 1. 测试环境

| 项 | 值 |
|---|---|
| GPU | NVIDIA GPU（8 GB 显存，消费级） |
| 引擎 A | faster-whisper `large-v3-turbo`（CTranslate2, float16） |
| 引擎 B | Fun-ASR-Nano-2512（800M，funasr 1.4.14，独立 venv `asr_eval`） |
| torch | 2.6.0+cu124 ／ Python 3.13.14 |
| 样本 | 同一条长视频（24:43，普通话口播，专名密集） |
| 短样本 | 上述音频 300–480s 切片，180.0s |
| 长样本 | 全长 1483s（24:43） |
| 方法 | 每个配置独立加载模型，测**纯 generate 耗时**（不含加载），RTF 由 funasr 自带统计交叉验证 |

## 2. 基准速度

| 引擎 / 配置 | 样本 | 转写耗时 | 实时倍率 |
|---|---|---|---|
| Fun-ASR-Nano，batch=1 | 180s | 35.5s | 5.07x |
| Fun-ASR-Nano，batch=8 | 180s | 35.6s | 5.06x |
| Fun-ASR-Nano，batch=8 | **1483s** | 286s | **5.08x** |
| whisper large-v3-turbo | 1483s | 77.4s | **19.15x** |
| whisper turbo + `initial_prompt` | 1483s | 71.6s | 20.71x |

**核心事实：Nano ≈ 5.1x 实时，whisper ≈ 19.2x，差 3.8 倍，且不随音频长度变化。**
（funasr 自带 `rtf_avg: 0.193`，与外部计时一致。）

## 3. 提速杠杆逐项实测（全部零收益）

### 3.1 `batch_size`（VAD 分段并发解码数）

| batch_size | 耗时 | 实时倍率 |
|---|---|---|
| 1 | 35.5s | 5.07x |
| 4 | 35.9s | 5.01x |
| 8 | 35.6s | 5.06x |
| 16 | 35.7s | 5.04x |

零收益。副产物：**batch=4/8 时个别词与 batch=1 不一致**（`电解材料`→`电极材料`、→`空间集团`），
batch=16 才与 batch=1 完全一致——存在解码非确定性。**用参数换不来速度，却可能换掉稳定性**，
故 `--infer-batch-size` 默认保留 1。

### 3.2 VAD 分段长度

| `max_single_segment_time` | 耗时 | 实时倍率 |
|---|---|---|
| 30s | 291.6s | 5.08x |
| 60s（当前配置） | 291.7s | 5.08x |
| 120s | 290.2s | 5.11x |

零收益。**推翻 SKILL 旧版结论**「跨多 VAD 段后实时倍率从 6x 降到 2x」。

### 3.3 热词成本

| 配置 | 耗时（180s） |
|---|---|
| 37 词热词 | 35.5s |
| 无热词 | 39.9s |

同量级（首轮含预热，无热词那轮排在最前）。**推翻旧版结论**「热词随每段重新注入、不是零成本」。
→ **不必为省时间砍热词**。

### 3.4 双进程并发

同一 180s 音频，各起一个 adapter 进程：

| 配置 | 墙钟 | 吞吐 |
|---|---|---|
| 单进程 | 93.2s（含加载 48.9s） | 1.93 音频秒/墙钟秒 |
| 双进程并行 | 179.4s（两进程 ASR 各 110–121s） | 2.01 音频秒/墙钟秒 |

**加速比 1.04x，效率 52%**——单进程已把 GPU 吃满，无闲置算力可挖。

## 4. 负结果：`initial_prompt` 无法弥补 whisper 的专名缺陷

**动机**：若能用 whisper 的 20x 速度 + 专名提示词拿到 Nano 级专名，即可绕开 4 倍时间代价。

**做法**：把 35 个专名（含曾毓群、陈棠华、ATL、磷酸铁锂…）拼成 `initial_prompt`
注入 turbo，与无提示版本对照，以 Nano 已产出的素材包为基准。

| 专名 | Nano | turbo | turbo + 提示 |
|---|---|---|---|
| 曾毓群 | 7 | **0**（写成「曾玉群」×5） | **0**（「曾玉群」×3） |
| 陈棠华 | 1 | **0** | **0** |
| 宁德时代 | 46 | 23 | 36 |
| 动力电池 | 31 | 30 | 29 |
| 磷酸铁锂 | 10 | 6 | 7 |

- **提示词确实有偏置作用**：`宁德时代` 23→36、`宁德` 24→38，速度不受影响（20.7x）。
- **但人名一个都没救回来**：`曾玉群` 错误在加提示后仍然存在。

**机理**：音近替代（曾毓群→曾玉群）是**声学层**的识别错误，`initial_prompt` 只在**解码先验层**
起作用——它能让模型"更愿意说出"某个词，但压不住声学上听错的结果。

**结论：不存在「whisper 速度 + Nano 专名」的中间方案。要人名正确只有 Nano。**

## 5. 结论与排期

1. **Nano 的 ~5x 是架构上限**：800M 自回归解码，单进程即打满 GPU。调用参数、分段策略、
   并发都动不了。要更快只能换硬件（更大显存才有意义）或换推理后端（如 vLLM，未验证）。
2. **排期按 5x 算**：10 小时音频 ≈ 2 小时。模型冷启动 48–52s，但**批量只付一次**——
   批量务必走 `--batch-file` / `library_queue.py`，不要逐条调用。
3. **引擎选择的代价是不对称的**：whisper 快 3.8 倍但人名错，Nano 慢但人名对。
   知识库条目的可检索性取决于专名是否正确，故专名密集内容（历史/地理/政经/人物）用 Nano 是
   正确取舍，4 倍时间是为"半年后还能搜到"付的费。
4. **不要再重复以下实验**：调 `batch_size`、改 VAD 段长、砍热词、开双进程、给 whisper 加
   `initial_prompt`、换 Qwen3-ASR-1.7B（专名 7/11 < Nano 10/11 且参数更大）。

## 6. 复现方式

```bash
# 短样本基准（同一切片，模型每配置重载）
PYTHONPATH= <asr_eval python> funasr_adapter.py --audio bench_180_16k.wav \
    --infer-batch-size <N> --out out.json --quiet

# whisper 对照（须先注册 CUDA DLL，否则报 cublas64_12.dll is not found）
python -c "import sys; sys.path.insert(0,'<skill>/scripts'); import bili_asr; bili_asr._setup_cuda_dlls()"
```
